Vault · distributed object storage

Storage that expects things to fail.

Vault splits every file into pieces, spreads them across independent machines, and quietly rebuilds whatever a failure takes away, so your data stays readable while hardware comes and goes.

See How Vault Works → About the Live Console

01

Machines fail. Quietly, and all the time.

At scale, something is always broken somewhere. A storage system has to assume it. These are the four failures Vault is built around.

Copies can't quietly drift apart in Vault: pieces are immutable and named by their content hash. A copy can only be missing or damaged, and both are detected.

02

One file, many nodes.

Each bucket has a durability policy that decides how a file is spread. Pieces go to different zones first, so one failing rack or room can't take them all.

03

Failure is expected.

With erasure coding 4+2, any four of the six pieces rebuild the file. Take nodes offline yourself and watch what still works.

In a real cluster Vault wouldn't wait: once a node is declared failed, repair starts rebuilding its pieces elsewhere. That's the next step.

04

Detect. Repair. Restore.

Recovery runs by itself, in the background, while the cluster keeps serving requests.

  1. 1Detect

    Every node is probed each second. A missed probe makes it suspect: new data avoids it, but nothing is moved yet, so a brief blip causes no churn. After a timeout (10 s by default) it is declared failed.

  2. 2Repair

    The repair service finds every chunk below its target and fixes the most endangered first. It copies a surviving replica, or rebuilds a missing piece from any four survivors. Rebuilt data is checksum-verified before it is stored.

  3. 3Restore

    New pieces land where the placement map wants them, so nothing needs a second shuffle. If the failed node comes back, the extra copies it still holds are trimmed.

05

How it's built.

The components of the actual implementation and the files they live in.

Client

Any HTTP client: curl, a script, the console.

Gateway core.py · api.py

Streams files in chunks, replicates or erasure-codes them, and writes to enough nodes to meet the bucket's quorum. Reads verify every byte and ask a second node if the first is slow.

Metadata metadata.py

SQLite in WAL mode. Objects, versions and piece locations change in single transactions, so a file becomes visible all at once or not at all.

Placement placement.py

Weighted rendezvous hashing, spread across zones. Adding a node moves only its fair share of data.

Storage nodes node.py

Each node is an independent server storing content-addressed blobs with a SHA-256 header. Writes are atomic; corrupt blobs are quarantined, never served.

In the background

Failure detector membership.py

Heartbeats every node: alive → suspect → failed.

Maintenance maintenance.py

  • repair restores missing copies
  • scrub re-verifies data at rest
  • anti-entropy reconciles nodes with metadata
  • rebalance moves data after membership changes
  • GC removes what nothing references

Erasure coding erasure.py

Reed-Solomon over GF(2⁸), implemented in the project.

06

Everything above, running for real.

The illustrations on this page are simplified. The console is not: it shows the state of an actual Vault cluster, read from its API every two seconds.

  • Node health from Vault's failure detector, and disk usage reported by each node.
  • Objects with upload, download and end-to-end SHA-256 verification.
  • Repairs and detections from Vault's own event log.
  • Fault injection: take a node down or flip a bit on disk, and watch recovery happen.

07

Engineering.

Small, dependency-free and tested under failure.

Language
Python 3.11+, standard library only. No third-party runtime dependencies.
Storage nodes
http.server; atomic, fsync'd writes; SHA-256 in every blob header.
Metadata
SQLite (WAL) with serializable transactions and compare-and-swap versioning.
Erasure coding
Reed-Solomon over GF(2⁸) with a Cauchy matrix, written for this project.
Placement
Weighted rendezvous hashing, interleaved across zones.
Console
Plain HTML, CSS and JavaScript with a small standard-library proxy. No build step.
Tests
39 backend tests, including crashes, partitions, bit rot, concurrent writers and a chaos run, plus 8 console tests. The suite passes under a 256-open-file limit.
Size
About 2,600 lines of Python for the system itself.
